# Fixed-protocol allocation completion

Allocation and alternative-protocol research have separate completion gates.
The production allocator must preserve the accepted logical publications,
acquisitions, matching, cuts, coactive command order and invocation contract.
Comparing independently certified physical maps is permitted within that graph.
Changing the protocol requires a new coverage/order, progress, matching and
finite-resource argument. It is not an allocation relabeling or an automatic
fallback after a failed sufficient construction.

| Evidence | Permitted conclusion | What remains open |
|---|---|---|
| Valid uniform assignment for the owned protocol and eligible pool | Physical allocation succeeds under the admitted context | Device compilation/execution and latency |
| Checked directional width exceeding the pool in an admitted execution | That identical fixed protocol cannot fit the pool uniformly | Other protocols, lifetimes or reservation contracts |
| All checked execution widths fit | These executions do not exclude the pool | A uniform reusable assignment |
| Unsupported export or failed sufficient assignment | Current allocator has not certified this request | Feasibility and minimum capacity |

The permanent capacity oracles now emit these distinctions as machine-readable
fields. Each result carries the input hash, admitted bindings and a digest of
ordered payload/command events. Uniform allocation, kernel compilation, device
execution and alternative-protocol analysis are separate outcome fields. A changed
command graph cannot silently inherit the prior witness. Instrumentation counts
are excluded from graph identity. The oracle's empty-payload feedback control
shows why inserting acknowledgments changes capacity without being mere relabeling.

These are not universal lower bounds for the kernels or hardware. A bound closes
the stated fixed-protocol feasibility question; it does not count as successful
kernel compilation. The earlier eleven-kernel campaign remains eight physical
successes, with no device qualification claimed here.

Alternative-protocol work is a separate backlog: establish whether a different
communication graph preserves the required payload order, then certify its
matching, progress, state and resource requirements. No ordering-changing repair,
extra barrier, runtime frontier analyzer, or implicit protocol replacement is
introduced by this milestone. Existing generic and sufficient allocators remain
available where their own contracts apply.
